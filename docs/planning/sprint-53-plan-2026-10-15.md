## P0: freezes

- [ ] **S53-01. Shader compilation freezes the game for 30-40 s on Windows.**
  - **Evidence:** the PC froze for 32 s after deploy, 36 s on the first frame after the Mothership dialogue, and 38 s on the retry. Each lines up with a jump in compiled shader programs. Peak programs rose from 206 at v2.4.16 to 468, and the worst freeze from 3.2 s to 38.4 s, across Sprint 52 uploads. The Deck shows the same moments at 5-9 s.
  - **Measure first:**
    - list `renderer.info.programs` by cache key on `v2.4.16-beta` and on the head, in the same start view;
    - count programs per source: new world-story and expansion models, shadow-depth variants, materials patched with `onBeforeCompile`, and props with practical lights.
  - **Then:**
    - share one program cache key across patched materials;
    - keep a fixed light budget, so streaming props never change the scene's light count and recompile every lit material;
    - make the startup warm-up compile what the first view really draws, with `compileAsync` and `KHR_parallel_shader_compile`, before control is handed over.
  - **Progress (2026-10-15):** measured and fixed on GPU; the Windows re-measure is still owed.
    - **Cause 1, lights outside the pool.** The warm-up compiled with 25 point lights. Then three camp beacons, the O2 indicator light and the bed-socket light took the count to 28, then 29, and a retry dipped it to 26. Every change recompiled every lit material. All five now go through `registerEnvLight`, which also ignores repeat registrations.
    - **Cause 2, an unused warm-up pass.** The warm-up compiled a direct, shadowless variant of every material that gameplay never draws. Adaptive quality keeps the composer and shadows on, so the warm-up now compiles only the composer variant.
    - **Result (GPU probe, head build):**

      | Measure | Before | After |
      | :--- | :--- | :--- |
      | Programs at deploy | 255 | 115-120 |
      | Programs added after deploy, streaming and a retry | +110 | +3 |
      | Counted point lights in gameplay | 25/28/29/26 | 24 throughout |

    - **Guard:** `tests/e2e/probes/shader-program-stability.spec.js` fails on the old code with counts `[25, 28, 29, 26]` and passes now. The unit tests are in `src/threeGame.envLightBudget.test.js` and `src/threeGame.shaderWarmup.test.js`.
  - **Accept:**
    - on the Windows machine, no main-thread task over 250 ms from deploy through the first 5 minutes, first life and retry;
    - shader programs at or below the release count, or explained;
    - the Deck re-measured on the same route.
- [ ] **S53-02. The scene is too heavy to hold frame rate.** At the end of the PC run: 7.6 M triangles, 890 draw calls, a 3.6 GB JS heap peak, and about 15 fps on both machines. Measure triangles and draw calls per prop source and set a room budget. Owner art stays: never crush props ([lived-in pass 2](lived-in-world-pass-2-2026-10-09.md)); use LODs, instancing and culling instead. Targets: the [remediation plan](playtest-remediation-steam-deck-and-pc-2026-10-12.md) p95s (Deck ≤ 33 ms, PC ≤ 16.7 ms).
  - **Progress (2026-10-15).** Measured on this RTX 2070 SUPER (the PC class in the QA session), with GPU compositing (headed Chrome on Xvfb).
    - **Headless measurements are misleading.** Headless Chrome composites in software and reads the canvas back each frame, so it reports ~8 fps whatever the settings.
    - **It is CPU-bound, not GPU-bound.** One change per run on a pinned map:

      | Variant | fps |
      | :--- | ---: |
      | High (the QA settings) | 28.3 |
      | Shadows off | 31.6 |
      | Post-processing off | 30.3 |
      | Blended floor off | 29.5 |
      | 70% resolution | 29.7 |
      | World detail low | 27.7 |

      The main thread is ~23 ms of JavaScript per frame.
    - **Where that time goes** (CPU profile, inclusive share of the main thread):

      | Share | Cost |
      | :--- | :--- |
      | ~34% | rendering: draw submission 12%, program switches 9%, shadow maps 6-10% |
      | 12% | the matrix pass (`updateMatrixWorld`), 9.5% of it chunk content |
      | 5-7% | per-object frustum culling (`projectObject`) |
      | 5.7% | `updateScatter` (fog-of-war raycasts, snail paths) |
      | 4.1% | `updateCamps` (nearby-prop prompts, model mixers) |
      | ~5% | forced layout from per-frame `clientWidth` reads |
      | 2.8% | cone-occlusion raycasts |

    - **Triangles:** at spawn, 1.2 M in the main view, 1.1 M in the key-light shadow and 0.9 M in the suit-light shadow. They cost GPU time, which is not the limit.
    - **Done:**
      - the cliff secret-path glows are one instanced batch per chunk, not one mesh per cell: ~1,200 fewer scene nodes (6,100-6,500 -> 3,500-4,500 per view), and the chunk matrix pass fell from 10.8-11.9% to 9.4-9.5%;
      - the container size is cached by a `ResizeObserver` (`getContainerSize`), so frames no longer force a layout;
      - the probe `tests/e2e/probes/scene-weight.spec.js` (per-pass, per-source triangles and draw calls along a walk).
    - **Also done (later 2026-10-15):** animated world props bank their animation time while off screen and beyond the key-light shadow's reach, and step on return to the same pose (`src/mixerCulling.js`). Profile at spawn: mixers 2.5% -> 2.2% (most props there are in reach; the saving grows with explored, mounted-but-off-screen chunks). The darkness overlay's layout read fell from 2.0% to 0.2%, confirming the size cache.
    - **Measured, not changed:**
      - **Program switches:** 167 per frame for 420 draws (116 programs); sorting opaque draws by program would cut them, but it changes draw order for coplanar surfaces, so it waits for a pixel-diff harness.
      - **Hidden nodes:** only ~8% of chunk nodes are hidden, so skipping them is not worth the risk.
      - **Prop models:** their sub-meshes (~1,200-1,400 nodes) could be merged per material only by working around effect anchors and articulated parts.
    - **Tried and reverted:** change-tracking for the chunk matrix pass. Node traversal, not matrix maths, is the cost; it saved under 1 point.
    - **Next, by size:**
      - batch the remaining per-cell chunk objects the same way (door decorations, wall-top and wall decorations), to cut nodes and culling;
      - sort or merge materials to cut program switches;
      - throttle the suit-light shadow and the cone/fog raycasts to every other frame where nothing visible changes;
      - re-measure on the Windows machine. This harness presents through Xvfb and caps near 30 fps, so fps gains do not show here.

## P1: the right operator, the right input

- [x] **S53-03. Switching class can leave the previous class on screen.**
  - **Owner:** on the Deck the hero select still showed the Scout after switching to the Tank.
  - **Route (from the capture):** pick the Scout, ENTER ARMORY, RETURN TO MAIN MENU, pick the Tank, ENTER ARMORY. The deployed class was correct, so this is presentation only.
  - **Suspects:** the hero preview's stale-request guard (`pendingPreviewType`, `heroPreviewRequestGeneration`), which can drop the Tank request after the door transition; and the preview being rebuilt lazily on menu entry since `56f74c81`.
  - **Accept:** a GPU probe that runs this route, plus every pair of class switches, and checks the model on the hero select and in the Armory.
  - **Fixed (2026-10-15).**
    - **Cause:** the Armory scene boots with the Scout. `setWeapon`, `setCharm` and `setChassisSkin` reload the operator with `activeClass`, which only changes once a load finishes. The weapon refresh during setup therefore reloaded the Scout and cancelled the newer class load.
    - **How bad it was:** a probe of the old code shows the Scout on the bench for **all six** ordered class switches. The owner's Deck timing hid it on some visits.
    - **Fix:** the scene tracks the requested class (`requestedClass`), and all three reload with it.
    - **Hero select:** it was already correct (the probe's screenshots).
    - **Guard:** `tests/e2e/probes/class-swap.spec.js` runs Scout -> Armory -> back -> other class -> Armory for every pair, asserting `window.armoryScene.getOperatorClass().shown`. It fails on the old code (6/6 Scout) and passes now.
- [ ] **S53-04. Deck controls are logged as keyboard.**
  - **Owner:** only the Deck's controls were used.
  - **Log:** the input mode flipped controller/keyboard 13 times, and both deploys recorded `deploy-input-provenance: keyboard`.
  - **To find:** which Steam Input action-set path emits key or mouse events (trackpads, back buttons, the menu set). Fix the classification so the deploy record reflects the real device and the prompts show the right glyphs.
  - This unblocks #53 evidence from logs (see the [controller navigation map](../design/controller-navigation-map.md)).
  - **Progress (2026-10-15).**
    - **Findings in the capture:** the "Hotkey Escape" entries are the game's own synthetic Back events (untrusted, which the mode check ignores). There is no key injection in Electron, and the renderer never reads the `menu_pointer` actions. So every switch to keyboard came from a trusted pointer event, and each unexplained one lines up with a modal opening or closing, or a phase change: hover updates under a resting cursor, or a warped cursor.
    - **Fix (`src/inputActions.js`):**
      - pointer movement switches to the mouse only from trusted mouse or pen moves that actually move: two within 250 ms totalling the 6 px jitter threshold (`createPointerIntentTracker`). A real mouse switches within two events; a lone jump or a zero-movement update does not.
      - a touch press no longer switches to keyboard (`pointerPressCountsAsMouse`).
    - **Diagnostics:** every `input-mode-changed` log now carries its `cause` (event type, pointer type, movement or key code). The next Deck capture will show the exact source if any switch remains.
    - **Still to confirm:** a controller-only Deck session with `deploy-input-provenance` reading `controller`.
- [ ] **S53-05. New players can squad-wipe on O2 before learning the bubble.** In the session the Scout walked into the cryo chunks and drained from 100% to 0% in 5 minutes, after choosing "run me through protocols". This is a design check, not a bug: have the tutorial teach O2 before the player can leave the bubble's range, or warn at 50%.
